## 2026-08-27 の対応

### ✅ App Store の「言語: 英語」を修正（commit 48d6653）

製品ページに「言語: 英語」と出ていた（iTunes Lookup の `languageCodesISO2A` が `['EN']`）。
`app.config.ts` に `locales` も `CFBundleDevelopmentRegion` も無く、既定の en のままだった。

- `locales: { ja: './assets/locales/ja.json' }` で `ja.lproj/InfoPlist.strings` を生成
- `CFBundleDevelopmentRegion: 'ja'`
- `CFBundleLocalizations: ['ja']` も明示

`.lproj` が実際にバンドルへ入るかはビルドしないと確認できないため、
Info.plist から直接読まれる `CFBundleLocalizations` を併記して確実にしてある。
prebuild で両キーと `ja.lproj` の生成は確認済み。**表示が変わるのは 1.53 を配信してから。**

### ✅ 年齢区分を実態に合わせて訂正 — 3者の食い違いが解消した

**ASC は同日中に復旧した**（下記の障害セクション参照）。復旧後に年齢制限指定の質問票を
全7ステップ読み出したところ、**「無制限のWebアクセス: はい」が誤申告**だと確定した。

根拠は推測ではなくコードにある。`src/features/article/loadRequestPolicy.ts`:

- トップフレームは **記事URL と `about:blank` 以外すべて `deny`**
- サブフレームは `isEmbedFrameUrl()` のホワイトリスト（YouTube 等の埋め込み）だけ許可
- 「元記事を開く」は `Linking.openURL` で**外部ブラウザ**へ逃がす＝アプリ内ブラウズではない

Apple の質問文は「ユーザはアプリ内の任意のWebページに移動したり、自由にWebを閲覧したりできます」。
どちらもできないので **いいえ** が正しい。**これだけを変更**して保存した。

| | 訂正前 | 訂正後 |
|---|---|---|
| App Store（iOS 26+ の新体系） | 16+ | **13+**（172か所）/ ブラジル・韓国・ベトナムは 12+ |
| App Store（iOS 26未満） | 17+ | **12+** |
| Play（IARC・8/27 更新済み） | 12+ | 12+（変更なし） |

**3者3様が解消した。** ただし反映は **1.53 を配信してから**（ASC に
「変更内容は次のアプリバージョンでリリースされます」と明記されている）。配信中の 1.52 は 16+/17+ のまま。

新しく追加された **「ソーシャルメディア」の質問は「いいえ」**（既定のまま維持）。
まとめくんのコメントは記事単位で、フィードで拡散する仕組みがないため。

#### 変更しなかったもの — 「汚い言葉または下品なユーモア: まれ」

2ch/5ch まとめの実態としては「頻繁」に寄せる余地がある。ただし
**Webアクセスの件と違って客観的な判定材料がない**（頻度の主観判断）。
根拠なく年齢区分を動かすのは避け、既存の申告を維持した。
上げる場合は新体系が 16+ に戻り、Play の 12+ との差が再び開く点に注意。

### 記録: ASC の `iris` API 障害（2026-08-27・同日復旧）

一時期アプリ配下のページが永久にスピナーのままだった。実測した内訳:

```
GET /iris/v1/apps/1546424384/appInfos?include=ageRatingDeclaration,... → 503
GET /iris/v1/apps?include=appStoreIcon,displayableVersions...          → 503
GET /iris/v1/alternativeDistributionDomains                            → 503
GET /olympus/v1/*（セッション・アカウント系）                            → 200
```

セッション系は通るのでヘッダーとアプリ一覧だけは描画され、
アプリ配下は `appInfos` が返らず描画されない、という切り分けだった。
**使用許諾契約の未同意とは無関係**（同意後も 503 が続き、その後ひとりでに回復した）。
Apple の公式システム状況にも掲載されなかった。

同じ症状に当たったら、**ページを見るのではなく `fetch('/iris/v1/apps/{id}/appInfos')` を
直接叩いてステータスを見る**のが早い。200 が返るようになってからリロードすれば復旧している。

## 🚨 最優先: AdSense/AdMob **アカウント全体が強制停止**(2026-08-15 〜 2026-09-14)

AdMob 管理画面は `signup/info/account-suspended` にリダイレクトされ、開けない。
AdSense のポリシーセンター(`adsense.google.com/.../policy-center`)で確認した内容:

| 項目 | 内容 |
|---|---|
| ステータス | **広告配信停止中**(アカウント単位。pub-6803082941924637 配下の全アプリ) |
| 期間 | **2026年8月15日 〜 2026年9月14日** |
| 理由 | **無効なクリックとインプレッション** |
| 影響 | 広告は表示されない / 支払いは保留 / 直近の収益が減額されることがある |
| 追加リスク | **停止期間中または終了後に別の問題が見つかると、アカウントは永久に無効** |

### 原因(強い状況証拠)

`src/lib/ads.ts` の本番/テスト切り替えが **`__DEV__` だけ**だった。
`__DEV__` は debug ビルドでしか true にならないため、

- EAS `preview` プロファイル(内部配布APK、`distribution: internal`)
- Play の内部テスト版
- ローカルの release ビルド

はすべて `__DEV__ === false` = **本番広告ユニット**を読み込んでいた。
実際、開発用エミュレータには 2026-08-13 10:45 に release 署名の 1.50(vc56) が入っており、
これは本番ユニットでインプレッションを発生させていたことになる。
Play Console の実測では**1か月間のアクティブデバイス数は 1、インストール 2件**で、
実ユーザーのトラフィックはほぼ無い。つまり計上されていたのは大半が開発者自身の操作であり、
Google から見れば「自己クリック/自己インプレッション」に見える。

### 対応(実施済み)

- `eas.json`: 各プロファイルに `env.EXPO_PUBLIC_ADS_ENV` を追加
  (`development`/`preview` = `test`、`production` = `production`)
- `src/lib/ads.ts`: `process.env.EXPO_PUBLIC_ADS_ENV === 'production'` のときだけ本番ユニット。
  **設定漏れはテスト広告に倒す**(収益が出ないのはすぐ気づけるが、本番ユニットへの誤トラフィックは取り返しがつかない)
- `src/lib/ads.ts`: `setRequestConfiguration` に `testDeviceIdentifiers` を追加。
  プロファイル判定は production ビルドまでは守れないため、製品版を実機で確認するときの二段目の防壁にする。
  端末IDは起動ログの `setTestDeviceIds(Arrays.asList("..."))` から拾い、
  `EXPO_PUBLIC_ADS_TEST_DEVICE_IDS` にカンマ区切りで並べる(`EMULATOR` は常時登録)
- `FeedAdCard` と `ArticleScreen` の広告枠: `onAdLoaded` / `onAdFailedToLoad` で
  実際に埋まったときだけ帯・区切り線・「広告」ラベルを描く。
  停止期間中に空の広告枠が残るのを防ぐ。BannerAd はマウントしたままなのでリクエストは続く

### 停止期間中の鉄則

1. **本番ユニットを絶対に踏まない。** 実機・エミュレータでの確認は必ずテスト広告で行う
   (上記の修正が入った 1.51 以降なら production ビルド以外は自動的にテストID)
2. **AdMob への審査リクエストは 9/14 以降にする。** アカウントが停止している間は
   「サイトの動作: ナビゲーション」を直しても広告は出ず、
   停止中に別の問題を指摘されると永久無効に近づく
3. アプリ側の改善(1.51)とストア掲載情報の是正は先に進めてよい

## ✅ 解決済み: AdMob ポリシー違反「サイトの動作: ナビゲーション」(2026-08-04 制限解除を確認 → 8/14 再発)

### 経緯

| 日付 | 出来事 |
|---|---|
| 2024-10-07 | 違反を指摘され「制限付きで広告配信中」に |
| 2025-03-24 | 審査リクエストが**不承認** |
| 2026-07-27 | 原因を特定し、コード修正(下記) |

対象は **Android (`com.matomebeta_app`) のみ**。iOS は指摘されていない。

### 原因(証拠画像から特定)

AdMob ポリシーセンターの証拠画像で、Google のレビュアーは**記事画面の「コメントを開く」ボタンを赤枠で囲んで**指摘していた。そのすぐ下にバナー広告(「開く »」CTA 付き)が並んでいた。

該当ポリシー: *「ナビゲーション用機能であると直感的に認識されるような配置で広告が表示されるページ」*

修正前の `ArticleScreen` では、広告に隣接するタップ要素が 3 つあった:

| 要素 | 広告との距離 |
|---|---|
| `fabRow`(コメントを開く / 稲妻FAB) | **16px** ← 指摘箇所 |
| `relatedSheet`(関連記事カード) | 0px |
| `CommentComposer`(入力欄・送信) | 0px |

さらにタブバー `ConvexTabBar` も高さ 50px で画面最下部にあるため、記事画面へ遷移すると**タブバーがあった位置にそのまま同じ高さの広告が入れ替わる**構造だった。

### 対応(1.44 で実施済み)

余白を数十px足す対症療法では、一度不承認になっている以上また通らない恐れがある。そこで**広告に隣接するタップ要素を構造的にゼロにする**方針を採った。収益を維持するため記事画面のバナーは残し、さらに一覧へインフィード広告を追加している。

| | Before | After |
|---|---|---|
| 記事画面の操作系 | 最下部に「コメントを開く」トグル + 稲妻FAB を浮かせる | **すべてヘッダーに集約**(画面下部はタップ要素ゼロ) |
| 記事画面の広告 | 最下部にバナー(50px)、ボタンと16px隣接 | 最下部にバナー(**維持**)+ 区切り線・「広告」ラベル・セーフエリア。占有は約85pt(旧構成の128ptから圧縮) |
| 関連記事シート | 下から出る(広告に密着) | **ヘッダー直下から降りる**(広告から最遠) |
| 一覧画面 | 広告なし | **Homeの「新着」のみ**、記事カードの間にインフィード広告(**収益追加**) |

コメント欄は旧版どおり **100%:0 ⇔ 50%:50 の上下分割を維持**した(既存ユーザーの操作感を壊さないため)。変わったのは開閉トリガーの位置だけ。

**変更ファイル**

- `src/features/article/ArticleHeaderActions.tsx`(新規)— ヘッダー右の操作クラスタ。`💬` コメントトグル(開いている間は `✕`)/ `⚡` 関連記事(0件時は非表示)/ 既存の `⋮` メニュー。アイコンのみだが `accessibilityLabel` で用途を読み上げる
- `src/features/article/ArticleScreen.tsx` — `fabRow`(トグル+FAB)を撤去してヘッダーへ移管。関連記事シートを `bottom:0` → `top:0` に変更。広告ブロックを再構成(`borderTopWidth:1`・背景 `appBar`・バナー左余白に重ねた「広告」ラベル・`insets.bottom`)。記事の表示面積を最大化するためバナー高さぴったりに詰め、クリアランスはコメント表示時のみ `commentAreaClearance` で確保する
- `src/lib/feedAds.ts`(新規)— 一覧の広告スロット計算。**先頭3件は広告なし・以降12件ごと・末尾は必ず記事**。ランキング順位がずれないよう元インデックスを保持する
- `src/components/FeedAdCard.tsx`(新規)— 記事カードと見間違えないよう、上下マージン12px(NewsCard は 4)・上下の区切り線・背景色を `appBar` に変更・「広告」ラベル常時表示
- `src/features/home/LatestList.tsx` — `withFeedAds` を適用。`getItemType` で FlashList のリサイクルを種別ごとに分離。**適用はここだけ**(人気/ランキング/検索/MyPageには入れない)
- `src/scraper/serialize.ts` — `head` に `padding-bottom:24px` を注入。最終行が広告ブロックの区切り線に張り付くのを防ぐ(ボタンが最下部に浮いていた頃は90px必要だったが、ヘッダー移管により不要になった)
- `src/theme/typography.ts` — 未参照になった `sizes.adBannerHeight` を削除(広告ブロックは余白で高さが決まるため固定値を持たない)

**MyPage(ブックマーク・履歴)には広告を入れていない** — 個人領域であり、件数も少なく誤タップリスクに見合わないため。

> ⚠️ **`ArticleScreen` の画面下部にタップ要素を戻さないこと。** 広告バナーとの隣接がこの違反の原因そのものであり、
> ボタンを下に戻すと再発する。操作を追加する場合はヘッダー(`ArticleHeaderActions`)に置く。

### 検討したが採らなかった案

| 案 | 却下理由 |
|---|---|
| ボタンを28〜80px上へずらすだけ | 一度不承認になっているため「少し離した」では通らない恐れ。広告バーが記事面積を奪う読みにくさも残る |

| コメントを右からのドロワーにする | 旧版の上下分割に慣れた既存ユーザーの操作感を大きく変えるため見送り |

   npx eas-cli@latest submit -p android --latest --non-interactive

   - **画面下部にタップできる要素が一切ないこと**(広告バナーの上はクリアランス帯)

   - ヘッダーの `⚡` で関連記事がヘッダー直下から降りること(関連0件なら⚡が出ない)
   - 記事の最終行が広告ブロックの区切り線に張り付いていないこと
   - キーボードを出してもレイアウトが崩れないこと

   一覧画面:
   - 広告カードが記事カードと明確に見分けられること(誤タップ耐性)
   - 先頭3件に広告が出ないこと / MyPage に広告が出ないこと
   - Ranking の順位番号が広告を挟んでもずれないこと
   - 無限スクロール・Pull-to-refresh が壊れていないこと
   - スクロールがカクつかないこと(FlashList のリサイクル)
